# 게임 최종 합격 검수 프롬프트

목표: 현재 게임의 모션·행동·경쟁전 판정을 끝까지 검수하고, 재현한 결함을 수정해 명시한 지원 범위의 합격 기준을 충족시켜라. 결론을 먼저 정하지 말고 증거로 판정하라.

지원 범위: macOS Apple Silicon의 데스크톱 Chrome, 절차적 도시와 홍콩 지도, 키보드·마우스와 표준 게임패드, 30/60/144 FPS에서의 시뮬레이션, 혼자 플레이와 2~8명 온라인 플레이, 저장소의 WebSocket 서버 및 운영 Supabase 경로.

성공 기준:

1. 이전 검수의 모든 P0/P1 항목을 현재 소스에서 재현하거나 수정됐다는 증거로 닫는다. 검사에서 빼거나 보고서 문구만 바꿔 닫지 않는다.
2. 39개 모션 전체 타임라인과 모션 전환, 기술 종료·중단·재시작·초기화, 낙하·착지·구르기·벽·옥상·양손 거미줄·웹 집·공중 묘기를 검사한다. 일반 상태로 복귀해야 하는 모션이 고정되지 않아야 한다.
3. 실제 입력, 메뉴·창 비활성화·재접속·동시 입력·예약 공격을 검사한다. 안내·동작·서버 피해 판정이 일치해야 한다.
4. 경쟁전의 이동·공격·벽 가림·피해·구조·목표·승패는 서버가 검증한다. 공격자나 피해자의 주장만으로 판정을 확정하지 않는다. 피해 확인을 무시한다고 무적이 되거나 시간 초과를 무조건 명중으로 바꿔 벽 관통을 허용해서는 안 된다.
5. DB 변경은 운영 외 환경에서 실제 PostgreSQL 함수·트랜잭션·권한으로 먼저 검사한다. 인증·Realtime을 대체한 검사, 단일 연결 검사, 운영 함수 읽기는 각각 그 한계를 표시한다. 운영 변경은 검증된 변경과 롤백 방법을 준비한 뒤 수행한다.
6. 현재 전체 테스트, 필요한 새로운 회귀 검사, 빌드, 실제 브라우저 장면과 온라인 시나리오를 통과시킨다. 오류·경고·성능 측정 결과를 보존한다.
7. 기존 기능을 삭제하거나 지도를 몰래 바꿔 통과시키지 않는다. 가짜 결과·과도하게 느슨한 임계값·수동 PASS·검사 제외를 금지한다. 비용 발생 작업이나 추가 권한이 필요하면 구체적인 필요 사항을 제시한다.

실행: 가장 먼저 남은 실패를 재현한다. 수정 전 실패 → 수정 → 같은 검사 통과 → 관련 통합 검사 순으로 진행한다. 환경이 막히면 가능한 독립 검증 환경을 구축하고, 유료 리소스를 임의로 생성하지 않는다. 소스·지원 환경·명령·실패·수정·검사 결과·미검증 범위를 파일로 남긴다.

판정: 모든 기준이 충족되고 재현된 P0/P1과 미검증 필수 항목이 0개이면 **“명시한 지원 범위에서 최종 합격”**으로 판정한다. 이는 모든 미래 상황의 무결함을 의미하지 않는다. 하나라도 남으면 FAIL 또는 BLOCKED로 표시하고, 부족한 증거를 숨기지 않는다. 결과를 좋게 보이게 하려고 “완벽”을 선언하지 않는다.

최종 출력: 합격/불합격/검증 차단 여부, 수정한 결함, 실행한 검증, 커밋·푸시·운영 적용 여부, 남은 항목과 필요한 구체적인 다음 조치. 보고서와 실행 증거를 링크한다.
