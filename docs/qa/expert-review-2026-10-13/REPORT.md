# 게임 전문가 관점 검토 — 2026-10-13

## 판정과 검증 범위

이동·애니메이션·설정·검증 기반은 상당히 구축되어 있다. 현재 가장 중요한 과제는 기능 개수를 늘리는 것이 아니라, 온라인 판정의 공정성, 플레이어가 이해할 수 있는 일관된 규칙, 이동 실력이 반복 플레이의 동기가 되는 구조를 완성하는 것이다. 장기간 플레이한 이용자의 승률·이탈률 자료가 없어 수치 밸런스 평가는 가설로 구분한다.

검토한 것은 현재 로컬 작업 디렉터리다. 기존 미커밋 변경을 보존했고 게임 소스와 운영 DB를 수정하지 않았다. 실제 33년 경력을 주장하는 것이 아니라 해당 수준의 검토 기준을 적용한다.

- 로컬 도시 브라우저에서 로비 → 혼자 플레이 → 점프 → 레이스 시작 → 메뉴를 확인했다. 첫 레이스 목표는 시작 고도 96m에서 약 92m 아래, 거리 약 100m로 표시됐다.
- 기존 5173 서버에서 로컬 화면을 검사한 뒤, 현재 소스를 실행한 5174 개발 서버에서도 혼자 플레이 진입을 확인했다.
- 기본 홍콩 지도는 75% 지형 준비를 거쳐 LIVE 상태로 로딩 완료된 것을 확인했다. 홍콩의 완전한 이동·전투 플레이 검증은 완료하지 않았으므로 그 체감 품질을 단정하지 않는다.
- `npm test` 및 `npm run build` 성공. 빌드의 메인 JS는 약 5.63MB, gzip 약 2.01MB이고 큰 청크 경고가 남는다.
- 추가 Node 재현 6개는 `reproduce.json`에 기록했다. 실제 WebSocket 로컬 서버 검사와 실제 게임 클래스의 최소 시나리오를 사용했다. 서버 내부 상태를 사용하는 검사 부분은 모드·시간 조건을 분리하기 위한 fixture이며 운영 공격 실험이 아니다.
- Supabase는 저장소의 최신 SQL을 읽었다. 운영 적용 상태를 이번 검토에서 조회하거나 변경하지 않았다.

## 먼저 고쳐야 할 오류와 규칙 불일치

### 1. P0 — 온라인 메뉴/비활성 창이 피격 면제로 연결됨 [재현]

`src/Multiplayer.js:307`은 일시정지 중 이동 갱신을 멈춘다. `scripts/rooms.mjs:126`과 최신 SQL `supabase/migrations/20261012235525_arena_correction.sql:207`은 공격자 또는 피격자의 마지막 이동이 1.5초보다 오래되면 공격을 거부한다. 결국 Escape 메뉴나 창 비활성화로 멈춘 도망자는 1.5초 뒤 공격을 받지 않는데 경기 제한 시간은 계속 흐른다.

재현: 공격 범위 내 도망자의 마지막 이동을 1.6초 이전으로 만들고 정상 경찰 공격을 전송했을 때 HP 100 유지. 실제 브라우저 메뉴 입력과 통합한 장시간 검사는 추가로 필요하지만, 입력에서 서버 거부까지의 코드 경로는 연결된다.

수정 방향: 온라인 메뉴는 서버에서 플레이어를 보호하지 않아야 한다. 마지막 확정 위치의 heartbeat와 접속 유효성을 구분하고, 비활성 플레이어의 피해 및 연결 종료 정책을 명시한다.

### 2. P1 — 예약한 두 번째 주먹은 모션이 나와도 온라인 피해가 없음 [재현]

`src/Combat.js:43`에서 공격 예약은 false를 반환한다. `src/main.js:415`는 true일 때만 온라인 공격을 등록한다. Combat 내부에서 나중에 시작한 예약 공격은 `pendingPunch`에 등록되지 않는다.

재현: 두 번째 잽 action id 2가 실제 실행돼도 온라인 공격 전송은 첫 번째의 1회뿐이었다.

수정 방향: 클릭 성공 여부 대신 실제 공격 action의 시작/타격 이벤트에서 온라인 요청을 한 번 등록하고, 취소·예약·재시작에도 중복 없이 연결한다.

### 3. P1 — 로컬 서버와 Supabase의 이동 검증 기준이 다름 [소스 확인]

로컬 서버 `scripts/rooms.mjs:105`는 20m 일회성 여유와 72m/s 누적 예산을 사용한다. 최신 Supabase SQL의 이동 검사는 패킷마다 `greatest(20, 경과밀리초*0.15)`를 허용한다. 100ms마다 20m 이동을 반복하는 입력은 SQL의 거리 조건상 통과 가능하다. 일반 게임의 최고 속도는 48m/s다.

특히 홍콩 경로에는 로컬 도시의 서버 충돌 검사가 없으므로 이 차이를 우선 다뤄야 한다. 현재 운영 DB에도 동일 SQL이 적용됐다는 것은 이번 검토에서 확인하지 않았다.

수정 방향: 두 서버에 같은 누적 예산과 상태 전이 규칙을 적용하고 동일 패킷 시퀀스로 회귀 검사한다.

### 4. P1 — 추락 복구 후에도 레이스가 활성 상태로 남음 [소스 확인]

`src/PlayerExperience.js:24`의 자동 복구 콜백은 묘기와 고스트만 중단한다. 레이스를 중단하거나 `TimeTrial.previousPosition`을 초기화하지 않는다. 따라서 시작점으로 순간 복귀해도 레이스가 계속되고, 복귀 전후 위치를 링 통과 선분으로 검사할 여지가 있다.

수정 방향: 자동 복구 시 해당 시도의 기록을 무효화하고 링·고스트·HUD를 함께 정리한다. 복구 선분이 실제 체크포인트를 통과하는 악용 경로는 별도 브라우저 재현이 필요하다.

### 5. P1 — 구조 시간에 연속 접속/갱신 보장이 없음 [재현]

`scripts/rooms.mjs:139`와 최신 SQL의 구조는 첫 접근 시각과 다음 접근 패킷 시각의 차이로 3초를 판단한다. 중간의 위치 heartbeat가 끊겨도 타이머를 취소하지 않는다.

재현: 구조 시작 후 3.1초간 이동 패킷이 전혀 없다가 같은 위치를 한 번 전송하자 쓰러진 팀원이 HP 50으로 구조됐다. 이것은 벽을 넘어 구조되는 것까지 재현한 결과는 아니다.

수정 방향: 최근 유효 위치가 연속적으로 확인된 시간만 누적한다. 추가로 현재 구조 조건은 거리만 사용하므로 얇은 벽·천장 너머의 구조를 허용할지 규칙을 정하고 가시선/바닥 검사를 검토한다.

### 6. P1 — 탈출 목표의 중복·간격·경로 길이를 검증하지 않음 [재현/소스]

`src/PursuitRules.js:7`은 시작점과의 거리만 확인하고 두 개 이상이면 채택한다. 서로 같은 목적지 두 개도 통과한다. 목표 인덱스를 목적지 수로 나누므로 두 지점은 A→B→A가 된다. 이는 의도된 왕복일 수 있지만 '목표 3개'라는 안내와 구별해야 한다.

중복된 A→A→A도 허용되는 validator를 재현했다. 일반 생성기가 실제로 중복 지점을 만들었다는 증거는 아니다.

수정 방향: 목적지 간 최소 거리, 중복 제거, 안전한 이동 가능성, 총 경로 길이 범위를 검증한다. 경기 인원별 목표 길이와 노출 시간을 맞춘다.

### 7. P2 — 수동 저장 위치가 자동 안전 위치 갱신으로 덮어써짐 [소스 확인]

저장 버튼과 자동 이동 기록은 둘 다 `progression.data.safe[city]`를 쓴다. `src/Progression.js:38`에서 안전한 바닥에 서면 같은 슬롯을 갱신한다. 특정 옥상을 저장해 두어도 이후 이동한 곳이 복귀 위치가 될 수 있다.

수정 방향: 사용자가 정한 북마크와 마지막 자동 안전 위치를 별도로 보관하고 복귀 버튼의 이름과 목적을 구분한다.

### 8. P2 — 최종 레이스 시간은 마지막 링 통과 순간과 다름 [재현]

`src/TimeTrial.js:174`의 구간 기록은 프레임 내 통과 비율을 보간하지만 최종 기록 `:183`은 프레임 끝 시간이다. 재현에서 마지막 링 구간 기록은 10.025초, 최종 기록은 10.100초였다. 프레임 속도/지연에 따라 기록에 불필요한 차이가 생긴다.

수정 방향: 최종 기록·최종 구간·고스트 종료 시각을 같은 보간된 통과 시각으로 맞춘다.

### 9. P2 — 개인 전투 규칙과 온라인 규칙이 화면에서 충분히 구분되지 않음 [소스 확인]

개인 연습은 잽 12, 스트레이트 17, 훅 32, 강공격 48 피해이며 방어와 회피 무적을 사용한다. 온라인은 모든 주먹을 25 피해로 처리하고 서버 피격은 CombatSystem의 방어·회피 무적을 읽지 않는다. 온라인에서 기력 HUD도 숨겨지지만 공격은 계속 로컬 기력을 소모한다.

개인/온라인의 수치가 다른 것 자체는 결함이 아니다. 동일 입력과 모션으로 서로 다른 효과를 주면서 안내가 충분하지 않은 것이 문제다. 강공격의 비용은 큰데 온라인 피해가 같으므로 선택 이유도 약하다.

수정 방향: 온라인 유효 행동과 기력을 보여 주고, 방어·회피의 실제 효과를 명시하거나 온라인 규칙으로 구현한다. 강공격은 별도 역할을 주거나 제거한다.

### 10. P2 — 거미줄 이동과 공격을 같은 발사 입력으로 처리 [소스 확인/설계]

`src/main.js:428,443`에서 이동용 줄을 붙이는 클릭도 온라인 web 공격을 요청한다. 실제 부착 지점과 공격 대상은 다르게 계산된다. 서버는 상대의 범위·고도·방향 조건으로 즉시 피해를 판정한다. '이동하려고 발사했는데 상대에게 피해', 또는 '벽에 붙은 줄인데 상대에게 명중'처럼 원인과 결과가 불명확해질 수 있다.

수정 방향: 이동/포박의 의도와 시각 효과를 구분한다. 전투용 발사는 목표 표식, 쿨다운, 별도 발사/명중 반응으로 읽히게 한다.

### 11. P2 — 묘기 안내와 점수 시스템에 작은 모순 [재현/소스]

- README는 공중 묘기 최대 배수를 2.5배로 안내하지만 실제 보상 StuntSystem은 최대 4배다. 다른 7종을 추가해 4배를 재현했다.
- `PlayerExperience.js:25`가 안내 콜백을 StuntSystem.add로 바꾸는데, add는 0점 이벤트를 바로 버린다. '묘기를 마칠 높이가 부족합니다', '줄을 놓고 T...' 같은 안내가 표시되지 않는 경로가 생긴다.
- 반복 감점은 착지 때 초기화된다. 쉬운 한 동작을 점프→착지로 반복하면 반복 감점을 피하며 누적 색상 보상을 얻을 수 있다. 이는 오류보다는 숙련 보상의 설계 문제다.

수정 방향: 안내와 점수 이벤트를 구분하고 배수 표기를 통일한다. 보상에는 누적 점수 외에 다양한 이동 성취도 섞는다.

### 12. P2 — 마지막 탈락자의 경기 종료 시점에 구조 안내가 남을 수 있음 [소스/설계]

마지막 도망자가 쓰러지면 즉시 경찰 승리로 종료한다. 따라서 마지막 탈락자는 구조를 기다릴 기회가 없고 2인전에서는 구조 기능 자체가 사용할 수 없다. 일반 탈락 안내는 '팀원이 가까이 오면 구조 가능'이다.

수정 방향: 즉시 종료는 합리적인 규칙으로 유지할 수 있다. 다만 마지막 탈락/2인전의 화면 문구와 상태를 구분하고, 경기 종료 시 구조 마커·목표 마커를 정리한다.

## 게임 설계에서 부족한 부분

### A. 이동 숙련을 써먹는 반복 플레이 목표

자유 스윙과 묘기 자체는 좋은 기반이다. 장기 목표는 색상 3종과 탐험 수치에 집중돼 있어 보상 이후 동기가 약해질 수 있다. 기존 레이스에 구간별 개인 목표, 다양한 이동 방식으로 얻는 숙련 배지, 경로 선택 결과와 재도전 비교를 넣는 것이 우선이다. 새로운 도시/코스/튜토리얼을 곧바로 늘리는 것은 별도 선택이며, 기존 기록에서 이전 작업은 이 세 종류를 의도적으로 제외했다.

### B. 추격전 인원별 균형

6명은 경찰 1 대 도망자 5, 7명은 경찰 2 대 도망자 5로 바뀐다. 도망자 중 한 명만 3개 목표를 끝내도 팀 전체 승리이고 목표 수는 인원과 무관하다. 인원이 늘 때 경찰의 실제 추격 부담이 어떻게 변하는지 실측이 필요하다.

개선: 2/4/6/8인에서 역할별 승률, 첫 명중까지 시간, 목표 완료 시간, 구조 횟수, 탈락 후 대기 시간을 기록한다. 목표 경로 길이·경찰 수·위치 공개 간격을 함께 조정한다. 현재 정보만으로 어느 팀이 반드시 유리하다고 단정하지 않는다.

### C. 레이스의 이동 경험과 경로 가독성

현재 링 배치는 각 위치의 바닥 높이+4m를 따른다. 시작 옥상에서 첫 링이 92m 아래로 내려가는 것을 브라우저에서 확인했다. 큰 고도 차이가 무조건 나쁜 것은 아니지만, 진입/탈출 가능한 부착점과 다음 링 시야를 함께 설계해야 의미 있는 스윙 코스가 된다. 보이는 다음 링 하나와 거리 화살표만으로 큰 하강 후 상승 경로를 미리 판단하기 어려울 수 있다.

개선: 현재 코스의 높이 변화·부착점·이동 가능한 연결을 검증하고 간단한 코스 미리 보기와 구간 기록을 제공한다. 메달 기준 `경로 직선거리/9`는 현재 초기 기준이므로 수직 이동 난도와 실제 기록 분포로 조정한다.

### D. 실패 후 학습과 재시도

전투 실패는 시작점 회복과 상대 제거로 끝난다. 어떻게 실패했는지, 다시 무엇을 시도해야 하는지 알기 어렵다. 자유 탐험도 같은 곳에서 무의미한 점수 반복으로 기울 수 있다.

개선: 받은 공격 종류·막기/회피 성공·유효타·완료 시간을 짧게 보여 주고 같은 연습을 한 번에 재시작한다. 팝업을 늘리기보다는 실패 원인과 다음 행동 한 가지를 연결한다.

### E. HUD의 중요도

일반 탐험에서 상단 세션 바, 레이스 패널, 속도/고도, 미니맵, 줄 상태, 조작 바가 함께 있다. 브라우저에서 FPS/P95 같은 개발 측정치도 기본 패널에 표시됐다. 이동 대상을 읽는 데 필요한 정보가 무엇인지 우선순위가 불명확하다.

개선: 전투/레이스/탐험에 따라 핵심 정보만 강조하고 기본 플레이에서는 성능 수치를 옵션으로 옮긴다. 게임패드 연결 시 화면 안내도 패드 버튼으로 바꾼다.

### F. 첫 실행 부담과 네트워크 의존

메인 JS gzip 약 2.01MB에 캐릭터·모션·도시 타일 다운로드가 추가된다. 기본 홍콩 지도는 외부 타일과 프록시 준비에 의존한다. 30초 지연 안내와 로컬 도시 대체 경로는 이미 존재하므로 이를 새로 만들라는 권고는 하지 않는다.

개선: 온라인/지도/연습 등 큰 모듈의 지연 로딩 가능성을 검토하고 실제 최초 조작 가능 시간과 지도 스트리밍 중 P95를 측정한다. 이번 브라우저의 50~60FPS 표시는 특정 환경의 관찰이며 기기 전체 성능을 대표하지 않는다.

## 권장 실행 순서와 완료 기준

1. 온라인 피격 면제, 예약 공격 누락, 두 서버 이동 검증 차이를 먼저 수정한다. 같은 입력 시퀀스를 양쪽 서버에 보내 같은 결과인지 확인한다.
2. 자동 복구 레이스 무효화, 최종 링 시간 계산, 연속 구조 조건, 목적지 검증, 저장 슬롯을 정리한다. 정상 플레이와 지연/복구 경로를 함께 검증한다.
3. 온라인과 연습의 행동 효과·기력·피해 안내를 맞추고 줄 이동/전투 효과를 구분한다.
4. 기존 레이스와 연습의 결과·재도전 화면을 개선한다. 이후 2/4/6/8인 플레이 데이터를 모아 밸런스를 결정한다.

기존 회귀 검사가 모두 통과해도 위 신규 사례는 검출되지 않았다. 테스트 개수보다, 플레이어가 실제로 할 수 있는 행동과 실패 경로를 검사하는 것이 필요하다.
