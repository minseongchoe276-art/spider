# 출시 검증 실행 방법

## 빌드와 운영 버전 고정

```sh
npm run build
npm run test:release-readiness
npm run verify:asset-http
npm run verify:release -- https://YOUR-SITE https://YOUR-ROOM-SERVER --all
```

빌드의 `dist/release.json`은 소스, 방 서버, DB 마이그레이션 소스, 배포 파일별 SHA-256과 역할별 전송 예산을 기록한다. `--all`은 실제 HTTP 응답의 압축 해제 후 원본을 모든 목록 파일의 해시와 비교한다. 생략하면 bootstrap 파일만 비교하므로 전체 파일 검증으로 보고하면 안 된다. `releaseId`가 정확한 빌드 산출물의 식별자다.

`/healthz`의 `backendId`는 실제 방 서버 코드와 로컬 의존 파일·lockfile의 식별자다. `databaseId`는 서버가 기대하는 마이그레이션 소스의 해시다. **운영 DB에 적용된 스키마가 같다는 증거는 아니다.** DB는 별도로 새 로컬 DB에 마이그레이션을 적용한 함수 정의·권한·search_path와 운영 DB의 읽기 전용 결과를 대조해야 한다. 이번 비교 SQL과 결과는 `qa/release-readiness-2026-10-25/operating-db-functions.json`, `expected-db-functions.json`, `db-comparison.json`에 있다. Edge 함수는 세 파일의 원본 SHA-256을 별도로 비교했다.

배포 전 새 버전 검수 파일을 보관하고, 이전 프런트/서버의 불변 배포 주소·revision과 DB 복원 방안을 기록한다. 스키마 변경이 있는 경우 데이터 삭제·롤백 영향을 먼저 검토한다. 배포 후 버전 검증이 실패하면 새 배포를 승인하지 않는다. 기존 서버의 `ready`만으로 버전 일치를 인정하지 않는다.

## 기기별 30~60분 브라우저 시험

필수 기기 범위는 실제 iOS Safari, 실제 Android Chrome, 목표 저사양 PC다. 브라우저 창 크기만 줄인 결과는 해당 기기의 시험 결과로 대체하지 않는다.

1. 기기·OS·브라우저 버전, 화면 크기·방향, 그래픽 품질, 충전 여부, 네트워크 조건을 관찰표에 기록한다.
2. 새 방문 또는 캐시를 비운 방문에서 로딩·첫 플레이 진입을 관찰한다. 로컬 서버의 캐시가 있는 진입 시간을 모바일 첫 방문 시간으로 보고하지 않는다.
3. 혼자 플레이에서 걷기·질주·점프·와이어 양손·집·벽·난간·구르기를 반복한다. 로컬 지도별 진입과 홍콩 지형 로딩/이동도 각각 시험한다.
4. 이동 중 조준/동작 버튼, 다중 터치, 손가락 이탈·취소, 화면 회전, 앱 전환 후 복귀, 도움말·지도·일시정지를 시험한다.
5. 게임의 활성 시간이 최소 30분이 될 때까지 이동·전투·임무를 반복한다. 메뉴·숨김·일시정지는 활성 성능 표본에 포함되지 않는다. 그 시간을 제외해 실제 체류 시간은 더 길어질 수 있다.
6. 메뉴 → 기기 · 연결 진단 → 진단 기록 다운로드로 JSON을 저장한다.
7. 발열·밝기 저하·브라우저 종료·배터리 시작/끝 잔량은 실제 기기에서 별도로 관찰한다. 진단 파일에 온도·배터리 측정값을 만들어 넣지 않는다. JS heap이 제공되지 않는 브라우저의 값은 `null`이며 0이 아니다.

```sh
npm run verify:device -- PATH/TO/diagnostics.json
```

이 명령은 빌드 일치, 활성 시간 1,800초, 프레임 존재, 기본 P95 34ms 한도를 검사한다. P95는 1ms 단위로 올림해 기록하므로 30 FPS의 33.33ms를 허용하는 기준이다. 이 통과는 온도·배터리·입력·누수까지 합격했다는 뜻이 아니다. 60 FPS 제품 목표를 채택하려면 별도의 더 엄격한 기준으로 판단한다.

진단은 최근 30분의 5초별 FPS/P95·최장 프레임·느린 프레임·렌더링 자원과, 세션 전체 누적 프레임·P95·최장 프레임을 기록한다. 1초 이상 꼬리가 P95에 들어가면 최장 프레임을 보수적으로 사용한다. 메모리의 첫 값과 마지막 값의 차이만으로 누수를 판정하지 말고 GC와 같은 장면의 반복 회복 여부를 확인한다.

홍콩 타일의 캐시 바이트·타일 로딩 상태·충돌 메시 누적은 기존 `?city=hong-kong&debugCity` 화면을 함께 관찰한다. 이 화면에는 카메라 좌표도 있으므로 자동 진단 JSON의 익명 관찰 기록과 구분한다. 이번에 그 좌표를 익명 내보내기에 추가하지 않았다.

## 8인 서버 장시간 시험

```sh
npm run test:soak -- 1800000
```

실시간 Node 물리 + 8개의 실제 로컬 WebSocket 연결을 시험한다. 매분 마지막 참가자를 같은 토큰·같은 ID로 복귀시키고, 다음 방을 생성하기 전에 이전 8명이 모두 나가 방이 정리되는지 검사한다. Node 메모리와 수신 이동 갱신 수도 기록한다. 짧은 시간을 전달한 실행을 “30분 시험”으로 표기하지 않는다. 이 시험은 GPU·모바일·8명의 실제 사람을 대신하지 않는다.

공개 프로토콜 검수:

```sh
ROOM_SERVER_URL=https://YOUR-ROOM-SERVER node scripts/check-public-custom.mjs
```

임시 방만 생성·정리하며 정원 초과, 팀전·개인전, 시작 보호, 지정 상대, 피해·탈락·승리·재경기를 확인한다. 이번 2인 공개 복귀 시험은 `qa/release-readiness-2026-10-25/check-public-two.mjs`에 있다. 참가자 8개가 한 검증 기계에서 접속했다는 것과 서로 다른 네트워크의 8명 시험은 구분한다. 실제 브라우저 관전 카메라도 별도로 확인한다.

## 신규 사용자와 역할별 균형 관찰

기초 안내를 해본 적 없는 참가자에게 설명을 미리 주지 않고 6단계 안내를 진행하게 한다. 막힌 단계·요청한 도움·실패 원인과 이해한 조작을 기록한다. 메뉴에서 안내를 다시 시작할 수 있다. 5종 임무는 완료뿐 아니라 중단과 다른 임무로의 교체도 관찰한다. 사람이 처음 플레이한다는 사실은 관찰자가 확인해야 한다.

온라인은 지도·인원·모드·역할 조합을 나눠 여러 경기를 진행한다. 진단에는 익명화한 역할·인원·지도·승패 관찰만 기록한다. 참가자별 출력은 같은 경기에 속할 수 있으므로 독립 경기 수로 합산하지 않는다. 실제 승률·완료율의 적정 표본과 목표는 제품 담당자가 결정한다.

```sh
npm run analyze:playtests -- SESSION-A.json SESSION-B.json
```

같은 세션에서 여러 번 내보낸 파일은 마지막 표본 하나만 사용한다. 버전·지도·화면·품질이 다른 성능 표본은 분리하고, 안내·임무의 완료/중단 시간과 역할별 승패 관찰을 집계한다. 이 자료는 로컬에서만 처리하며 자동 전송하지 않는다. 난이도가 적정하거나 재미가 있다는 결론을 자동으로 만들지 않는다.

## 자산과 출처

```sh
npm run inventory:assets
```

`docs/asset-inventory.json`은 공개 자산별 크기·SHA-256·컴파일 원본 경로·출처 증거·미확인 상태를 기록한다. `config/asset-provenance.json`에 실제 확보한 원본 링크·제작자·표시 조건·라이선스 증거를 연결한다. 라이선스 문서 하나를 관련 없는 파일 전체의 허가로 확대하지 않는다. 원본 링크·배포 근거를 확인하지 못한 항목은 `needs-review`로 남긴다.

빌드 목록은 bootstrap / 캐릭터와 컴파일 모션 / 원본 복구용 모션 / 필요할 때 불러오는 코드 / 기타 지원 파일로 구분한다. 이 분류는 **모든 캐릭터 자산이 첫 프레임 전에 다운로드된다는 뜻이 아니다.** 원본 FBX는 컴파일 모션이 실패했을 때의 복구 경로이므로 유지한다. JS·CSS·JSON·SVG·WASM·GLB·FBX에 Brotli/gzip을 미리 생성하고 Node 서버가 협상해 전송한다. 다른 정적 호스트가 `.br` 파일을 자동으로 제공한다고 가정하지 말고 그 호스트의 실제 HTTP를 검사한다.
